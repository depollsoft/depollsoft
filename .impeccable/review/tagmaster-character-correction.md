## Exact causes

- **iOS background removal is explicit.** `iOS/tagmaster/tagmaster/DPAppDelegate.m`, `setUpBackground:` near line 231, replaced the original aspect-fit `screenbackground.png` image and table background view with a grouped solid color. The original image occupied the view width between vertical offsets 60 and 44. `TMTheme.swift:154–168` instead template-tints the asset at 0.10 label alpha; `DPHomeViewController.m` puts that mark in a 64-point footer. That is not background preservation. `TMTheme.canvas` and `surface`, plus Home's `UITableViewStyleInsetGrouped`, establish the gray-field/white-card treatment visible in the capture.
- **Android removed the image layers, not the asset.** Original `res/layout/meview.xml`, `tagmasterview.xml`, and `tagdetailview.xml` placed a full-size, centered `ImageView` using `@drawable/ic_barberpole` behind content. Current roots omit it; `meview.xml` and both detail layouts paint `colorBackground`. The original vector and iOS raster are unchanged between commits. Android's original pole tints were `#11333333` in light and `#11DDDDDD` in dark. Reuse the real assets rather than the new `ic_barberpole_mark` navigation icon.
- **iOS added a second navigation level.** `TMRootController.swift` creates three separate navigation stacks inside a tab controller and enables a wide-window sidebar. Home's Find action switches stacks through `focusSearch()`. Browse adds collection segments; `DPTagViewController.m:158–244` adds four tag segments on phones and three beside the summary on tablets. The tablet capture visibly retains both global and local navigation.
- **Android reuses global-navigation shapes for local content.** `MeActivity.kt` binds Home/Browse/Search to a pager and bottom bar or rail. `TagBrowseFragment.kt` adds `TabLayoutMediator` for catalog collections. `TagDetailActivity.kt:121–139` binds a separate four-page pager to the same bottom-bar/rail idiom through `tagdetailnavigation`. The control position changes meaning from app destinations to tag sections. This existed locally before, but adding the new global shell makes the ambiguity worse.

## Correction contract for both apps

Restore the familiar flow: **Home → Browse/Search → Tag**, with native pushes and Back returning to the actual caller. Home may also open a favorite, random tag, or called-out ID directly. Remove the new global root tabs and tablet global rail/sidebar. Keeping the shell would retain duplicate Find/Search entry points and competing section controls; eliminating it is simpler for users and reuses the original navigation model. It requires deliberate route rewiring, not merely hiding the bar.

First Home viewport: existing handwritten Tag Master wordmark and Settings utility; one prominent Find a tag action; visible Browse entry; compact Random tag and Open tag ID actions; Favorites, followed by Teachable Tags with an always-available entry. Use normal rows and separators rather than a giant opaque action card or repeated filled pills. Attribution remains reachable below content. Preserve existing list data and truthful empty states.

Browse/Search is one catalog task: query field, a clearly labeled collection/sort menu for Latest, Rating, Downloads, and Classic, existing filters, then results. Do not turn collection choices into another navigation bar. Home's Browse opens the catalog without a query; Find opens the same task with search ready. Keep existing query semantics and result controllers where possible.

Tag opens with its title, key/pitch action, Sheet Music, and access to Learning Tracks immediately available. Favorite/teachable state and Share remain native toolbar/menu actions. Summary is the opening workspace, not a fourth competing tab. Details and Videos are plainly labeled content destinations. On phone, use rows/buttons to push Tracks, Details, or Videos from that workspace. Each returns to the same tag. Avoid replacing the global bar with local tabs.

On tablets, use available width for the tag summary/actions alongside the selected material, initially tracks when available or details otherwise. Put labeled material choices within the tag workspace, not in an app-style rail. Home and catalog retain readable content widths. Narrow windows and accessibility text collapse to the phone stack without losing tag, selected material, query, or scroll position.

The real pole must be centered behind Home, catalog/results, and the tag workspace and its content pages, with original proportions and recognizable page-scale weight. Extend the existing background helper to relevant utility screens. Keep sheet music/PDF and video content unobscured. Use one background per visible workspace, not duplicated poles in each tablet pane. Begin with the original asset/tint behavior, then adjust only for measured readability. Remove unnecessary full-pane paint; use local semantic backplates behind text/controls when needed. A tiny footer, navigation glyph, or image hidden under opaque views fails this requirement. Keep the wordmark, familiar blue, and native body typography; invent no theme or metaphor.
